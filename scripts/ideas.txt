# Stack token optimizers without breaking the cache

The "ultimate" Claude Code token toolkit is not a pile of compressors. It is an orchestration layer that puts each existing tool where it does the most good and keeps all of them away from the prompt-cache prefix. The three named tools barely overlap. **TokenSave** cuts tool-output tokens at the source by answering code-navigation questions from a local symbol graph. **Headroom** compresses the tool output and logs that still arrive. **Caveman** shortens the model's replies, and its companion tools shrink always-loaded memory files and MCP tool descriptions. The gap between claimed and measured savings matters for planning. Caveman's "65–75%" falls to about **1–3% of a real bill**, because output tokens are a small share of Claude Code spend. Headroom's own code-search figure was revised from **92% to 21%**. TokenSave's 94% comes from one user's 10-question benchmark. Provider prompt caching sets the main constraint. Cache reads cost about **0.1x** base input and writes cost 1.25–2x, so any layer that rewrites bytes already sent can raise cost while lowering token counts. The design that follows has six parts: a frozen static prefix, input shaping before tool calls, output filtering when results first enter context, an observe-only proxy, provider caching and context editing, scoped output terseness, and batched compaction. Those parts form the layered architecture described below. No source has tested any pair of these tools together. The unmet needs are a single measurement harness, coverage of built-in Read/Grep output, reversible lossy filtering, and conflict linting.

## Three tools target three different parts of the bill

The tools are complementary because each targets a different token category. A Claude Code request has five main parts: a static prefix (system prompt, CLAUDE.md, tool definitions), conversation history, fresh tool results, the model's visible output, and reasoning tokens. Input and context dominate the bill. Output is a sliver.

| Tool | What it is | Mechanism | Budget slice targeted | Integration |
|---|---|---|---|---|
| **TokenSave** | Rust MCP server | Local libSQL code graph with embeddings and FTS5; 34–37 read-only query tools | Tool-output and file-read tokens (avoided rather than compressed) | `tokensave install --agent claude` |
| **Headroom** | Python library, proxy, MCP server or agent wrapper | CacheAligner, then ContentRouter, then a type-specific compressor; reversible retrieval (CCR) | Tool outputs, logs, files, RAG chunks, new history | `headroom wrap claude` or `headroom proxy` |
| **Caveman** | Claude Code skill or plugin | Terse-style instruction re-injected every turn; companion tools rewrite memory files and MCP descriptions | Visible output; static input via companions | Plugin marketplace or curl installer |

**TokenSave** extracts functions, classes, methods, imports, type relationships and complexity metrics into `.tokensave/tokensave.db`. It includes vector embeddings and FTS5 search, and it syncs incrementally using content hashing and a file-watching daemon ([docs.rs USER-GUIDE](https://docs.rs/crate/tokensave/3.4.4/source/docs/USER-GUIDE.md)). Its tools fall into groups: core lookup, callers/callees/impact, code quality (dead code, circular dependencies, god classes), structural, git-aware (diff, PR context, test map), and porting. The tool count went from 34 in v3.4.4 to 37 in v4.x ([claudemarketplaces](https://claudemarketplaces.com/mcp/aovestdipaperino/tokensave)). It is the smallest of the three projects but releases quickly. crates.io showed **v7.16.0, updated 2026-10-22, with about 6,158 downloads** ([crates.io](https://crates.io/crates/tokensave)). Incremental re-sync after a small change took about 21 ms on one reviewer's machine. A `tokensave discover` command mines Claude Code history to estimate which past navigation steps the graph could have answered ([DEV](https://dev.to/comic_sans/tokensave-an-mcp-server-that-saved-me-millions-of-tokens-while-coding-4phl)). Several unrelated tools have similar names, including Token Savior, token-saver-mcp and cc_token_saver_mcp ([Glama](https://glama.ai/mcp/servers/Mibayy/token-savior)). Pin the exact repository `aovestdipaperino/tokensave`.

**Headroom** describes itself as a local layer that compresses "tool outputs, logs, files, and RAG chunks before they reach the LLM." Its ContentRouter sends JSON to SmartCrusher, code to an AST-aware CodeCompressor, and prose to a small HuggingFace model, Kompress-v2-base ([GitHub](https://github.com/chopratejas/headroom)). CodeCompressor is built on tree-sitter ([DEV review](https://dev.to/andrew-ooo/headroom-review-60-95-llm-token-compression-2026-4e32)). Its CCR (Compress-Cache-Retrieve) design keeps originals in a local cache and injects a `headroom_retrieve` tool so the model can recover the full content. Lossy compression therefore stays reversible. Its CacheAligner flags volatile content that would break the provider's prefix, and the README says Headroom **compresses only new content and never rewrites prompts** ([GitHub](https://github.com/chopratejas/headroom)). It also has an opt-in output "verbosity steering" mode (`HEADROOM_OUTPUT_SHAPER=1`), cross-agent memory, and `headroom learn`, which mines failed sessions and writes corrections into agent config files. It bundles RTK for shell output and can delegate to lean-ctx ([DEV review](https://dev.to/andrew-ooo/headroom-review-60-95-llm-token-compression-2026-4e32)). The live GitHub page showed 79.1k stars, but an older snapshot showed about 1,269 ([ecosyste.ms](https://awesome.ecosyste.ms/projects/github.com%2Fchopratejas%2Fheadroom)). Treat its popularity as unverified.

**Caveman** makes no model, tokenizer or runtime changes. It is a `SKILL.md` plus a hook that re-injects the terse-style instruction every turn ([Implicator](https://www.implicator.ai/caveman-claude-code-skill-cuts-output-20-your-bill-barely-notices-2/)). It has intensity levels lite, full and ultra, plus Classical-Chinese "wenyan" variants. The companion tools do more for cost than the core skill:

- `/caveman:compress` rewrites CLAUDE.md and other memory files and keeps a `.original.md` backup.
- `caveman-shrink` is an MCP stdio proxy that compresses the description fields returned by `tools/list`, `prompts/list` and `resources/list`, and leaves code, paths and identifiers untouched.
- `/caveman-stats` reads session JSONL to report real token usage.

Source: [DEV review](https://dev.to/andrew-ooo/caveman-review-the-claude-code-skill-that-cuts-65-of-tokens-2boe). The core skill **does not touch reasoning tokens**.

Several adjacent tools fill slots the named three leave open:

- **RTK** (about 84.7k stars) filters shell output for more than 100 commands through a Claude Code PreToolUse hook. Its README admits the hook fires only on Bash, so **built-in Read/Grep/Glob output is not intercepted**. It estimates tokens as bytes/4 ([rtk-ai/rtk](https://github.com/rtk-ai/rtk)).
- **Aider-style repo maps** use tree-sitter and personalized PageRank to fit a ranked symbol map into a token budget, 1,024 tokens by default ([agentpatterns.ai](https://www.agentpatterns.ai/context-engineering/repository-map-pattern/)).
- **Serena** (LSP-based navigation) and **Zilliz Claude Context** (hybrid embeddings plus BM25, claiming about 40% savings) offer alternative code-retrieval engines to TokenSave ([noqta.tn](https://noqta.tn/en/blog/semantic-codebase-indexing-ai-coding-agents-2026)).
- **ccusage** parses local Claude Code logs for cost reporting ([npm](https://npmjs.com/package/ccusage)).

The strongest levers are provider-side. In Anthropic's own evaluations, **Tool Search with `defer_loading` cut tool-definition context from about 77K to 8.7K tokens (−85%)** and raised MCP accuracy, for example Opus 4.5 from 79.5% to 88.1%. Programmatic tool calling cut tokens by 37% on complex research tasks ([Anthropic Engineering](https://anthropic.com/engineering/advanced-tool-use)). Anthropic's context editing reportedly cut consumption by 84% over a 100-round eval and improved agentic search by 29% (39% with the memory tool). These are first-party numbers reported secondhand ([The Decoder](https://the-decoder.com/anthropic-claims-context-engineering-beats-prompt-engineering-when-managing-ai-agents/)). They are the only techniques in the notes that report quality gains rather than losses, so a toolkit should enable them by default and build on top of them.

## Claimed savings shrink as measurement gets more careful

Every headline figure loses ground under scrutiny. Each loss follows from what the figure actually measured.

| Tool | Claimed | Best available measurement | Why the gap |
|---|---|---|---|
| Caveman | 65–75% output tokens | 12–30% of output; **~1–3% of total bill** | Verbose baselines; output is 0.6–2.5% of spend |
| Headroom | 60–95% on JSON/logs; earlier 92% on code search | Its own current table: 21–57% on agent scenarios | Self-revised; seeded offline script; no independent benchmark |
| TokenSave | 94% | Same figure: one user, 10 navigation questions | Per-question, not per-session; edits, tests and reasoning still cost tokens |

The Caveman case is the most thoroughly measured. Several independent tests ([Implicator](https://www.implicator.ai/caveman-claude-code-skill-cuts-output-20-your-bill-barely-notices-2/)):

- A 72-prompt, three-arm test found Caveman beat vanilla output by 23%, but beat a plain **"be concise" instruction by only 4%**.
- Another tester measured 12% on coding tasks.
- A Next.js session went from 11,200 to 8,900 output tokens.
- The author conceded on HN that real-world savings are "closer to 20–30%."

The same source puts output tokens at 0.6–2.5% of a typical Claude Code bill, which caps the cost impact at about 1–3%. A separate reviewer found a one-line "be brief" instruction captured most of the savings, and a hand-written six-line prompt beat the full skill on quality per token ([DEV review](https://dev.to/andrew-ooo/caveman-review-the-claude-code-skill-that-cuts-65-of-tokens-2boe)). A reproduction attempt found no committed API-harness results. It also found the eval snapshot measured characters rather than tokens, and that "no fidelity / accuracy evaluation exists for any arm" ([pantheon-org](https://pantheon-org.github.io/agentic-context/benchmarks/juliusbrussee-caveman/)). Caveman is worth adopting for its compress and shrink companions and for faster, more readable output, not as a cost lever.

Headroom revised its own figures sharply. The current README table, generated by a seeded offline script, shows 21% on code search, 57% on SRE debugging, 42% on codebase exploration and 30% on issue triage ([GitHub](https://github.com/chopratejas/headroom)). An earlier version claimed 92%, 92%, 47% and 73% for the same scenarios ([DEV review](https://dev.to/andrew-ooo/headroom-review-60-95-llm-token-compression-2026-4e32)). To its credit, it is the only one of the three that publishes accuracy evals: GSM8K unchanged at 0.870, BFCL 97% at 32% compression, SQuAD v2 97% at 19% compression. All were self-run at N=100. Latency is negligible: 0.21 ms p50 on 10K-token JSON. It labels output-token savings as counterfactual estimates unless measured against a 10% holdout ([GitHub](https://github.com/chopratejas/headroom)). That holdout discipline is a good design to copy.

TokenSave's 94% compares about 53,900 baseline tokens with about 3,000 graph-answer tokens across 10 questions on a 1,115-node graph ([DEV](https://dev.to/comic_sans/tokensave-an-mcp-server-that-saved-me-millions-of-tokens-while-coding-4phl)). The official guide states no savings percentage. A comparable tool's history shows how fragile such numbers are. Token Savior claimed 97.9% on a private benchmark, re-measured −59% new tokens and −45% cost with high variance, and withdrew an earlier re-measurement because **the tools were never actually called** ([Glama](https://glama.ai/mcp/servers/Mibayy/token-savior)). Retrieval MCPs save nothing unless the agent chooses to use them. Tool-call adoption rate is therefore a metric in its own right.

The independent literature supports the same caution. A six-method study of prompt compression found that **every method increased hallucination**, mainly through information loss. It also found that compressing input changed output length in model-specific directions: longer for GPT-3.5-turbo and GPT-4o-mini, shorter for Claude-3-Haiku ([arXiv 2505.00019](https://arxiv.org/pdf/2505.00019)). Stacked layers interact, and no source has measured any pair of these three tools together.

## Prompt caching decides which layers are safe to stack

Caches match exact prefixes. That single fact determines the toolkit's main design rule. Anthropic cache reads cost about 0.1x base input. Writes cost 1.25x with the 5-minute TTL and 2x with the 1-hour TTL, so a 5-minute write needs about 2–3 reads to break even ([agentpatterns.ai](https://www.agentpatterns.ai/context-engineering/prompt-caching-architectural-discipline/)). The cache breaks when you add or remove tools mid-session, switch models, put timestamps or metadata in the prefix, have subagents re-emit a changed prefix, or reorder or replace earlier messages. Keep-last-N truncation is the worst case: shifting every later message guarantees a full miss ([TokenPilot write-up](https://codex.danielvaughan.com/2026/07/03/tokenpilot-cache-efficient-context-management-codex-cli-prompt-cache-compaction-eviction-cost/)).

The pricing implies a concrete threshold. Compare a proxy that re-compresses the full history on every turn with leaving that history cached. The proxy turns a 0.1x read into a 1.25x write. It needs about a **12.5:1 compression ratio on that prefix just to break even**. Agent transcripts almost never compress that well without heavy loss. Three things follow: compress at ingestion, never at replay; make every transform deterministic or append-only; and give each tool result its final form before it first enters context.

Applying that rule to the three named tools:

- **Headroom is cache-safe by design**, since it touches only new content. Prompt caching covers the stable prefix and Headroom covers the dynamic output after it ([DEV review](https://dev.to/andrew-ooo/headroom-review-60-95-llm-token-compression-2026-4e32)). Its own docs warn that mid-session prefix changes invalidate the KV cache, and that native caching beats it for fixed long system prompts.
- **TokenSave** does not interact with the cache. It only changes which tool results get produced ([DEV](https://dev.to/comic_sans/tokensave-an-mcp-server-that-saved-me-millions-of-tokens-while-coding-4phl)). But adding its 34–37 tools mid-session would invalidate the cache, so register it before the session starts.
- **Caveman** carries the main untested risk. Its per-turn re-injected instruction is a recurring payload, and no source documents how it interacts with caching. The terse instruction belongs in the stable system prompt or an output style, frozen per session.
- **`/caveman:compress`** rewrites CLAUDE.md. It is safe as a one-time offline step and cache-hostile if run mid-session.

The overlaps that need explicit guards are narrow. **Headroom's `HEADROOM_OUTPUT_SHAPER` duplicates Caveman**, so enable only one. Headroom bundles RTK, so a separately installed RTK hook would double-filter Bash output. Claude Code's PostToolUse output replacement races when several rewriting hooks share a matcher, so allow at most one per matcher ([agentpatterns.ai](https://www.agentpatterns.ai/tool-engineering/posttooluse-output-replacement/)). Stacking TokenSave and Headroom is complementary but will show diminishing returns. TokenSave's results are already compact JSON, so Headroom's SmartCrusher has little left to remove.

Compaction is the hardest case. A compacted request loses cache reuse immediately afterward, but can still cost less in total. A 15k uncached request can beat a 100k request with 90k cached, so "measure several turns, not just one" ([flaviocopes.com](https://flaviocopes.com/agent-prompt-caching/)). TokenPilot shows the cache-aware approach ([TokenPilot write-up](https://codex.danielvaughan.com/2026/07/03/tokenpilot-cache-efficient-context-management-codex-cli-prompt-cache-compaction-eviction-cost/)):

- It canonicalises volatile fields (timestamps, absolute paths, schema versions) into static placeholders.
- It slims environment output at ingestion and keeps full payloads in an artefact registry.
- It evicts in batches, every three turns being best.
- It reports **61–87% cost reduction**. On one benchmark, cache-miss tokens rose from 6.18M to 8.89M while cost fell from $8.31 to $3.22. Cache hit rate alone is therefore the wrong objective.

Context rot favours dropping content over paraphrasing it. Chroma's study of 18 models found performance degrades with input length even on simple tasks, and focused ~300-token prompts beat ~113k-token full prompts on LongMemEval across all models ([Chroma Research](https://www.trychroma.com/research/context-rot)). Layers that drop or isolate (tool-result clearing, subagents, graph lookups) have both cost and quality on their side. Layers that rewrite (abstractive summaries, token-level compression) carry hallucination risk.

## A seven-layer architecture maps onto Claude Code's extension points

Claude Code already exposes most of the insertion points the toolkit needs. PreToolUse hooks can rewrite tool inputs. PostToolUse hooks can replace what the model sees through `hookSpecificOutput.updatedToolOutput`. A secondary source says that from v2.1.121 (April 2026) this applies to all tools, not only MCP tools ([agentpatterns.ai](https://www.agentpatterns.ai/tool-engineering/posttooluse-output-replacement/)). This is the cache-safe ingestion hook RTK lacks for Read and Grep. Treat it as version-sensitive: a later issue reports it silently ignored for built-in Bash and WebFetch on v2.1.173 ([claudeissues #67442](https://claudeissues.com/issue/67442-posttooluse-updatedtooloutput-silently-ignored-for-built-in-tools-bash-webfetch)). A gateway attaches through `ANTHROPIC_BASE_URL`. It must forward `anthropic-beta` headers and keep up with new Claude Code capabilities, or features break ([Claude Code docs](https://code.claude.com/docs/en/llm-gateway)). Subagents explore in clean windows and return condensed summaries of roughly 1,000–2,000 tokens ([howaiworks.ai](https://howaiworks.ai/blog/anthropic-context-engineering-for-agents)).

The reference pipeline below assigns each existing tool a layer and states the cache rule that layer must obey. It is a synthesis; no published design combines all of these.

| Layer | Purpose | Existing tools to slot in | Claude Code hook point | Cache rule |
|---|---|---|---|---|
| L0 Static prefix | Minimal, frozen system prompt, CLAUDE.md and tool set | `/caveman:compress` (offline), caveman-shrink, Tool Search `defer_loading` | CLAUDE.md, output style, MCP config | Freeze per session; canonicalise volatile values or move them to the tail |
| L1 Input shaping | Fetch less | **TokenSave**, repo map, Serena; PreToolUse flags (`--quiet`, line ranges) | MCP, PreToolUse `updatedInput`, skills | Safe: nothing has entered history yet |
| L2 Ingestion filtering | Shrink what still arrives | **Headroom** (MCP or wrap mode), RTK for Bash | PostToolUse `updatedToolOutput` | Safe if applied before first insertion; keep a raw artefact |
| L3 Proxy | Meter, budget, route | LiteLLM, Helicone, Headroom proxy in observe mode | `ANTHROPIC_BASE_URL` | Read-only on bodies already sent |
| L4 Provider | Discount repeated input | Prompt caching (1h TTL via `ENABLE_PROMPT_CACHING_1H=1`), context editing | Native | Delegate history trimming here |
| L5 Output | Shorter replies | **Caveman** lite/full *or* `HEADROOM_OUTPUT_SHAPER`, never both | Output style or system prompt | Must be static; scope by task class |
| L6 Post-hoc | Reclaim the window | `/compact`, batched eviction, NOTES.md | Native, PreCompact | Batch it; append summaries to the tail |

Each layer has a reason for its tool choices. At L0, Anthropic's deferred loading is the strongest single lever ([Anthropic Engineering](https://anthropic.com/engineering/advanced-tool-use)). caveman-shrink then compresses whatever descriptions remain loaded, including TokenSave's dozens of tool schemas. At L1, TokenSave's static graph should be backed by a CLAUDE.md rule telling the agent to query the graph before grepping, because MCP retrieval tools save nothing unless called ([agentpatterns.ai](https://www.agentpatterns.ai/context-engineering/repository-map-pattern/)). A git post-merge hook should trigger `tokensave sync`, since the graph goes stale after `git pull` ([DEV](https://dev.to/comic_sans/tokensave-an-mcp-server-that-saved-me-millions-of-tokens-while-coding-4phl)). At L2, Headroom's CCR retrieval tool and TokenPilot's artefact registry follow the same principle. The PostToolUse transcript keeps only the replacement, so a filter that discards the original is unrecoverable ([agentpatterns.ai](https://www.agentpatterns.ai/tool-engineering/posttooluse-output-replacement/)). Every lossy filter should write the full output to disk and leave a path in the summary.

L3 is deliberately thin. Gateways are the right place for budgets, attribution and audit, and the wrong place for rewriting message bodies. A proxy also changes billing. While a gateway credential is active, requests are billed per token to the credential owner and claude.ai subscription limits stop applying ([Claude Code docs](https://code.claude.com/docs/en/llm-gateway)). This matters for anyone running Headroom's proxy mode on a Pro or Max plan. At L5, the Chain of Draft evidence argues for scoping terseness by task. Few-shot CoD kept Claude 3.5 Sonnet within about 4 points of CoT on GSM8K (91.4% vs 95.8%) at about 21% of the tokens. Zero-shot, it fell from 90.4% to 65.5% ([arXiv 2502.18600](https://arxiv.org/html/2502.18600v2)). Ship terse modes with examples, and relax them for hard reasoning tasks and small models.

The toolkit itself should be a Claude Code plugin with three parts: hooks, a skill and an output style, plus an optional observe-only gateway. A single YAML config would carry per-layer enable flags and per-matcher rules. It would also include a conflict linter that refuses known-bad combinations: two rewriting hooks on one matcher, Caveman together with the Headroom output shaper, RTK installed alongside Headroom's bundled RTK, MCP servers registered mid-session, and dates or SHAs in CLAUDE.md. Order layers by expected impact. The ranking in the notes is cache hit rate first, then tool-definition deferral, then tool-result clearing and compaction, then output filtering, then retrieval, then cheaper-model routing. Output terseness comes last for cost purposes.

## Measure dollars per accepted task, not tokens saved

The tools' built-in counters can't be summed into a single savings figure. RTK estimates tokens as bytes/4 ([rtk-ai/rtk](https://github.com/rtk-ai/rtk)). TokenSave reports a self-reported cumulative counter (about 17.6B tokens worldwide). Headroom exposes `headroom_stats`. Caveman reads session JSONL. Each counts only its own category against its own counterfactual. Summing them double-counts, because TokenSave avoids reads that Headroom would otherwise have compressed. A critique on r/ClaudeCode makes the key point: savings can shift tokens between buckets, so the real tests are **cost per accepted diff and cache hit rate** ([DEV review](https://dev.to/andrew-ooo/headroom-review-60-95-llm-token-compression-2026-4e32)).

Use provider usage fields as the source of truth. Track uncached input, cache-read input, cache-write input, output tokens, request count and latency for every turn ([flaviocopes.com](https://flaviocopes.com/agent-prompt-caching/)). ccusage already parses these from Claude Code's local logs ([npm](https://npmjs.com/package/ccusage)). Report results the way TokenPilot does: task score, dollar cost and cache-miss tokens side by side, in both isolated and continuous session modes ([TokenPilot write-up](https://codex.danielvaughan.com/2026/07/03/tokenpilot-cache-efficient-context-management-codex-cli-prompt-cache-compaction-eviction-cost/)). That format exposes trade-offs a token count hides, such as TokenPilot's 87% saving arriving with a score drop from 63.4 to 60.8.

The experiment design has five parts:

- **Fixed task suite.** Use real repository tasks with automated acceptance checks, such as tests passing or a diff accepted.
- **Cheap baseline arm.** Run each layer against an "off" arm and also against a one-line "be concise" arm. The Caveman evidence shows a trivial prompt can capture most of the gain ([Implicator](https://www.implicator.ai/caveman-claude-code-skill-cuts-output-20-your-bill-barely-notices-2/)).
- **Persistent holdout.** Keep a 10% holdout in daily use, as Headroom does, so output-token effects are measured rather than estimated ([GitHub](https://github.com/chopratejas/headroom)).
- **Retrieval adoption.** Record how often the agent actually calls the retrieval tools, given the Token Savior episode.
- **Multi-turn accounting.** Measure across several turns, because compaction's benefit appears only after the first miss.

Add layers one at a time, so interactions between them, such as input compression changing output length ([arXiv 2505.00019](https://arxiv.org/pdf/2505.00019)), can be attributed to a specific layer.

## Integration gaps are the opportunity; supply chain and silent loss are the risks

The notes point to six unmet needs a new toolkit could fill. None is a new compressor.

1. **Unified, deduplicated accounting.** No tool attributes savings across layers against one counterfactual, and no source has tested any pair of these tools together.
2. **Built-in tool coverage.** RTK leaves Read, Grep and Glob output unfiltered ([rtk-ai/rtk](https://github.com/rtk-ai/rtk)). A PostToolUse filter for those tools, with version detection for the `updatedToolOutput` regressions, closes the most obvious hole.
3. **Reversible filtering as a shared service.** Headroom's CCR and TokenPilot's artefact registry are separate implementations of one idea. A toolkit-wide artefact store would let every lossy layer keep originals.
4. **Cache-safety verification.** A regression test should fail a configuration when the cache read:write ratio drops. Prefix canonicalisation in the style of TokenPilot is not yet available for Claude Code.
5. **Task-success evaluation.** No SWE-bench-style evaluation of any token optimizer on coding-agent task success was found. The CoD evidence comes from 2024-era models on arithmetic tasks ([arXiv 2502.18600](https://arxiv.org/html/2502.18600v2)).
6. **Adaptive policies.** Terseness could vary by task class, and the retrieval index could resync on git events.

The largest risk is security. A proxy that holds API keys is a high-value target. Malicious **LiteLLM 1.82.7 and 1.82.8** releases were published to PyPI on March 24, 2026. The payload sat in `proxy_server.py`, and a `.pth` file made it run on any Python startup. It stole SSH keys, cloud credentials, Kubernetes tokens and CI secrets, and tried to spread to every Kubernetes node ([BleepingComputer](https://bleepingcomputer.com/news/security/popular-litellm-pypi-package-compromised-in-teampcp-supply-chain-attack)). The precautions are:

- Pin and hash-verify every dependency.
- Prefer client-side hooks for content filtering, since hooks never see API keys.
- Give developers scoped gateway credentials and keep provider keys server-side.
- Log metadata rather than full prompts by default.

The lookalike forks around all three tools add typosquatting exposure. So does an unrelated "rtk" crate on crates.io ([rtk-ai/rtk](https://github.com/rtk-ai/rtk)). Telemetry is on by default in Headroom ([GitHub](https://github.com/chopratejas/headroom)). TokenSave sends a token-count POST by default, which can be disabled, and runs a GitHub version check that cannot be disabled ([DEV](https://dev.to/comic_sans/tokensave-an-mcp-server-that-saved-me-millions-of-tokens-while-coding-4phl)). RTK's engine and proxy are under BUSL-1.1 rather than Apache-2.0, which matters if the toolkit will be redistributed ([rtk-ai/rtk](https://github.com/rtk-ai/rtk)).

Quality risks are quieter. Compression raises hallucination ([arXiv 2505.00019](https://arxiv.org/pdf/2505.00019)). Output sanitizers can hide real errors ([agentpatterns.ai](https://www.agentpatterns.ai/tool-engineering/posttooluse-output-replacement/)). Caveman's ultra mode drops caveats and edge cases ([DEV review](https://dev.to/andrew-ooo/caveman-review-the-claude-code-skill-that-cuts-65-of-tokens-2boe)). TokenSave's static graph misses dynamic dispatch, reflection and macros, and returns stale answers between syncs ([DEV](https://dev.to/comic_sans/tokensave-an-mcp-server-that-saved-me-millions-of-tokens-while-coding-4phl)). A gateway that falls behind Claude Code releases breaks features silently ([Claude Code docs](https://code.claude.com/docs/en/llm-gateway)). One item remains unresolved in the notes: Anthropic's terms for routing subscription OAuth traffic through third-party proxies were not checked against primary sources. Verify them before shipping a proxy mode aimed at Pro or Max users.

## Conclusion

The value of this toolkit is not in compressing harder. It is in deciding where in the pipeline each transform runs. Compression has a natural ceiling set by caching economics. Once the prefix is cached at 0.1x, the remaining money sits in new tool output, cache misses and wasted reads. TokenSave and Headroom target exactly that, and Caveman barely touches it. The best first release is therefore conservative: provider-native deferral, caching and context editing turned on; TokenSave and Headroom at ingestion; Caveman's companions used offline; and a measurement harness that ranks configurations by dollars per accepted task.

The harness is likely to matter more than any individual layer. Every number in this space, including the 92%, 94% and 75% figures, has either been revised or remains unreplicated. The project that publishes reproducible, task-success-anchored, cache-aware measurements of stacked configurations would be the first to show what "ultimate" actually means, and that evidence would let the toolkit swap in better compressors as they appear.
